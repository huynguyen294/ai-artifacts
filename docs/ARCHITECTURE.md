# Architecture

```text
Artifact skill + Work Session skill
   | resolve (optional window discovery) / create / wait / inspect / advance-and-wait / join
   v
AI Artifacts MCP -- discovers live windows and coordinates review rounds
   |
   +-- ~/.ai-artifacts/artifacts/<id>/
   |     artifact.json + artifact.md + comments.json
   |     + optional submission + optional artifact-connection.json
   |
   +-- ~/.ai-artifacts/conversation-registry/<session-id>/
   |     conversation.json (v2) + instructions.md + layout.json + registered-artifacts/<artifact-id>.json
   |
   +-- ~/.ai-artifacts/session-types.json
   |
   v
VS Code extension windows -- publish heartbeats, match connection target, open editor / session tab
   |
   v
React webview -- renders ReviewApp (Markdown, comments, Sessions nav, direct Inspect prompt) & SessionApp (two-column Session Manager)
```

## Ownership boundaries

- The artifact skill handles explicitly requested artifacts, window selection, exact review handles, complete Markdown, feedback, and decisions. Its short Session bridge supplies optional arguments; omission creates/inspects standalone without clearing an existing active Session. The Work Session skill owns one active Session per chat, success-only New/Join/switch, Instructions, and catalog refresh. Session membership does not identify or switch the chat's active Session.
- The MCP server discovers live VS Code windows, exclusively creates schema-v6 artifacts in global storage, commits schema-v1 window-routing requests, manages schema-v2 Work Sessions with fail-closed v1 preflight (`CONVERSATION_MIGRATION_REQUIRED`), and advances review rounds. It generates IDs and review sessions, validates paths and candidate selection tokens, owns transient waiter registration, issues one-time round tokens, and commits round transitions transactionally.
- Each extension host window publishes fresh canonical workspace roots plus its stable instance ID, focus hint, and active-file context. It validates connection targets and artifact bindings, opens only requests addressed to its own instance ID, serves sessions and artifact queries, executes validated Work Session metadata/layout/membership mutations, and writes user comments/submissions. It is also authorized to execute narrow atomic patches to `artifact.json` for user-requested `title` and `kind` (Type) updates without modifying `updatedAt`, `reviewRound`, `createdAt`, `reviewSessionId`, Markdown, comments, or submission state.
- The webview renders sanitized CommonMark/GFM, provides inline comments, session navigation, direct inspect prompt copying, and metadata title/type editing in `ReviewApp`, as well as responsive multi-column Work Session management, in-session filtering, and ZIP export in `SessionApp`, sending typed messages to the extension host. It has no direct filesystem or process access.
- `src/shared` is the single contract boundary used by the MCP, extension host, and webview.
- An agent explicitly asked to author feedback may write `comments.json` and optionally create a `revise` submission in `review-submission.json`, following the artifact skill's AI-feedback reference. This exception does not grant lifecycle management or require takeover; user/AI conflict handling is outside its scope.

## Lifetime model

```text
artifact lifetime > waiter lifetime > chat-turn lifetime
```

An artifact is per-user data representing a review session. Its lifetime is bounded by the configured retention period (`agentPlus.artifactRetentionDays`, default 30 days); expired artifacts are permanently deleted when the extension activates. Global pinning does not exempt artifacts from retention. Global archiving (`artifact-ui-state.json`) hides items from the active sidebar by default while preserving searchability; similarly, global session archiving hides sessions from the sidebar and schedules them for permanent deletion after 30 days of archiving. In contrast, the in-session Archived zone (`layout.json.archived`) is a local categorization zone within a specific Work Session. A waiter is an in-memory connection from one MCP request to one exact artifact identity; non-waiting advances may change the round while the request stays pending. A chat turn may end or interrupt that request without changing the artifact.

Cancellation and takeover alone close watchers/timers and release waiter ownership only. They do not edit `artifact.json`, `artifact.md`, `comments.json`, `review-submission.json`, or `artifact-connection.json`; only an explicit reconnect intent may commit new routing state during inspection. MCP restart loses active waiters and tokens, but a validated inspection can issue a fresh token from the persistent schema-v6 state.

## Lifecycle tools

1. `resolve_artifact_window` accepts an optional `query` string matched against candidate label, active file, and folder paths. It reads fresh VS Code window snapshots and returns candidates grouped by window; each candidate includes `candidateId`, `windowInstanceId`, `focused`, `label`, `folderCount`, `folders`, `activeFile`, and an opaque `selectionToken`. It returns `status: "matched"`, `status: "selection-required"`, or `status: "not-found"`. It is read-only and never creates lifecycle files.
2. `create_artifact` creates review round 1, registers the artifact under `~/.ai-artifacts/conversation-registry/<artifactConversationId>/` (accepting optional flat fields `artifactConversationId?: string` and `conversationName?: string`; omitting both creates a standalone artifact without session registration), commits connection revision 1, and immediately returns the exact handle, optional `artifactConversationId`, and connection metadata. By default, it routes to the currently focused window (or sole live window); when focus is ambiguous across multiple windows, it returns `WINDOW_SELECTION_REQUIRED` requiring retry with `connection: { targetMode: "explicit-window", selectionToken }`. The official skill supports fixed and open kinds, defaulting to `plan` or `implementation-plan` when creating plans.
3. `wait_for_artifact_review` checks the expected round at attachment and attaches the single waiter to the artifact, or immediately returns an existing submission. An attached waiter can receive a later round; result validation and token issuance use that current submitted round. Accepts optional `artifactConversationId` and echoes it in the returned result.
4. `inspect_artifact_review` reads the current manifest, Markdown, comments, optional submission, connection state, and hashes, returning optional `artifactConversationId`. Accepts optional flat fields `artifactConversationId?: string` and `conversationName?: string` to register or update the artifact in a session; omitting both operates in standalone mode. With `intent: "reconnect"`, it re-evaluates the currently focused window (or explicit window candidate) and atomically increments the connection revision with a new open-request ID; ambiguous candidates require `connection.selectionToken`. With `takeover: true`, inspection first aborts and drains the prior waiter. It can grant a token from saved comments even before submission, or a chat-update token on an empty round when `intent: "explicit-chat-update"` is supplied.
5. `advance_and_wait_for_artifact` consumes an exact-state round token, optionally replaces Markdown, advances the round, resets comments/submission, and by default attaches a waiter for the new round. Accepts optional `artifactConversationId` and echoes it in the returned result. Optional `noWait?: boolean` defaults to `false`; `true` requires a valid UUID `artifactConversationId` before token claim or mutation, commits through the same transaction, then returns without registering a waiter, preserving any existing waiter. Only a waiting advance is rejected while another waiter exists in the same process. Its commit result contains the handle/link, identity, title/kind, new round/hash, echoed Session ID, and `waited: false`, without `decision`, `comments`, `nextAction`, or a new token. This parameter boundary does not verify chat Join state, registry existence, or membership; the Session skill supplies the active ID and selects the mode for direct updates. Creation always waits; standalone requests and review-feedback processing retain their existing flow. Omitting Markdown preserves its exact bytes and SHA. Both wait and advance preserve existing connection state and cannot rebind the artifact.
6. `join_session` accepts `sessionId` and optional `artifactId`. When called with `sessionId` only, it returns the shared session context read-only without window resolution, waiter interaction, or token issuance. When called with both `sessionId` and `artifactId`, it executes the shared inspect core for that artifact and returns both `session: SessionContext` and `inspection: FlatInspection`.

The default flow is create -> wait -> submitted decision. Both waiting tools return the complete validated `comments` document for every submitted decision, with the feedback list at `comments.comments`. This is the same snapshot validated against the round, artifact hash, comments hash, and submission, returned identically in text JSON and `structuredContent` without an extra inspection to fetch feedback. It applies equally to existing submissions and decisions received during an active wait, for every MCP client and model.

The non-waiting commit result is returned identically in text JSON and `structuredContent` but is not a submitted decision. The agent records its round and continues authorized work rather than fetching absent comments or starting a waiter. A later update needs a fresh inspection token, and a later review attaches a waiter on the current round only if none is already active. The direct-update inspection does not need takeover to bypass a waiter guard in non-waiting mode. Post-commit errors preserve `ADVANCE_COMMITTED`: waiting mode hints wait recovery, while non-waiting mode hints inspection without replay or automatic waiting. No registry, routing, UI, or schema changes are required for this mode.

Review (`revise`) grants a round token and `nextAction.type: "process-review-feedback"` for any artifact kind. Its instruction applies the same feedback policy as chat inspection: answer questions visibly in chat before waiting, replace Markdown only for requested changes, then advance and wait in the same turn using the retained exact artifact handle, returned round, and token. Question-only Review preserves the current Markdown bytes/SHA. Feedback needing clarification leaves the token unconsumed until clarified; managed lifecycle files must not be edited directly while processing saved feedback, and conversational answers stay in chat. Proceed (`approve`) and Just save (`save`) end only the current round and do not automatically advance. When processing a submission, the waiter re-reads the latest on-disk manifest so user edits to title and type are immediately reflected. For `plan` and `implementation-plan`, the Proceed result additionally carries `nextAction.type: "execute-approved-plan"`; this is runtime authorization to execute all approved in-scope actions immediately in the same turn. For other artifact kinds, Proceed returns `nextAction.type: "approved"` to acknowledge approval and conclude review without automatic implementation. Just save returns `decision: "save"` without `nextAction`; the skill asks for a destination and copies the Markdown without executing the proposed work. Neither terminal decision grants a round token, and both may return an empty comments list. Artifact-bearing lifecycle results include an RFC 8089 `artifactUrl` and regular Markdown `artifactLink`; neither is a custom-editor deep link. Join-only returns `{ session }` without an artifact handle or link.

The chat-escape flow differs only in transport: it cancels the live waiter and inspects the exact retained handle instead of receiving a Review submission. Classification, chat answers, optional Markdown replacement, clarification, advancement, and waiting behavior are shared with Review. If no feedback exists, the skill reattaches to the same round unless the user explicitly requested edits in chat (via `intent: "explicit-chat-update"`). Reconnecting an already approved or saved artifact is explicit and must not repeat the prior command.

Within one MCP process, only one waiter may own an artifact. Round tokens are in-memory, single-use, expire after one hour, and bind the artifact, session, round, artifact hash, comments hash, and submission presence/hash. Tokens have sources `submitted-review`, `chat-inspection`, or `chat-update` (which requires replacement Markdown with a different SHA). A token is consumed only after a successful transaction commit. Lifecycle errors retain readable text and add typed recovery metadata (`code`, retryability, next-tool hint, token reuse, same-handle requirement, and optional current round), preventing blind replay when commit state is uncertain.

## Persistent protocol

Schema v6 is the sole live lifecycle protocol:

- `artifact.json` identifies the schema-v6 artifact, title, session, and current round without repository ownership fields.
- `artifact.md` contains the complete current document.
- `comments.json` contains saved comments bound to the current round and artifact hash.
- `review-submission.json` appears after Review, Proceed, or Just save.
- `artifact-connection.json` is optional schema-v1 UI-routing state containing only `windowInstanceId`, `connectionRevision`, `openRequestId`, `source`, and `updatedAt`.
- Work Session registry under `~/.ai-artifacts/conversation-registry/<sessionId>/` stores schema-v2 `conversation.json` (`sessionId`, `title`, `typeId`, `createdAt`), primary instructions in `instructions.md`, `layout.json` (ordering across `working`, `references`, `archived` zones), and per-artifact index files under `registered-artifacts/<artifactId>.json`. The strict metadata reader accepts an optional legacy `instructions` string; effective instructions come only from Markdown (empty if absent), and metadata writers omit the inline field. Reads do not migrate or rewrite legacy data. Writes are atomic without file locks; `Session.updatedAt` is dynamically computed on read from `max(createdAt, ...registeredAt)`. Global session types are stored in `~/.ai-artifacts/session-types.json`.

Advancing always increments the round and resets handled comments. A question-only advance uses the existing Markdown unchanged. Schemas v3/v4/v5 are rejected and are not live-migrated.

`artifact.json` remains the source of truth for artifact ID; connection state never duplicates or overrides it. Connection revisions start at 1 and increment once per successful create/reconnect commit under an artifact-scoped lock. Revisions provide ordering and diagnostics, while unique open-request IDs deduplicate filesystem events. Connection writes are atomic and do not change Markdown bytes/SHA, comments, submission, review round, or round tokens.

## Workspace registry

Each running extension window writes an atomic snapshot under `~/.ai-artifacts/managed/workspaces/` (or `CODEX_ARTIFACTS_REGISTRY_DIRECTORY`) and refreshes it every 15 seconds. Schema-v2 snapshots expire after 45 seconds and contain canonical workspace folders (or empty array for folderless windows), focus state, and the active file/root when available. The registry publisher prunes snapshots, retaining at most 10 snapshots and removing files older than 7 days.

Window routing for creation defaults to the focused live window (or sole live window). Generic reconnect routing prioritizes: sole live window, validated advisory artifact-window affinity (where the agent's cached ID matches the stored connection and is fresh in the registry), and unique focused window. When multiple live windows exist and focus/affinity is ambiguous, `create_artifact` or `inspect_artifact_review` returns `WINDOW_SELECTION_REQUIRED` with candidates and opaque selection tokens. Agents present candidates using concise labels instead of raw UUIDs and retry using `connection: { targetMode: "explicit-window", selectionToken }`.

## Filesystem safety

- Artifact IDs are generated by the server and directories are created exclusively as direct children of `~/.ai-artifacts/artifacts/`.
- The exact global handle is canonicalized and bound to the manifest artifact ID. Nested, escaped, linked, workspace-local, and wrong-home paths are rejected before read or mutation.
- On POSIX, managed directories are tightened to owner-only `0700` and lifecycle files to `0600`. Windows relies on the user account and filesystem ACLs and makes no POSIX-mode guarantee.
- Canonical containment is checked before mutation; linked artifact storage paths are rejected.
- Create rollback may remove only the exact newly allocated directory.
- Advance stages the next round and restores prior files if commit fails. A narrow in-place fallback handles Windows editor locks.
- Activation cleanup: when the extension host activates, a best-effort asynchronous retention cleanup enumerates validated schema-v6 direct children of `~/.ai-artifacts/artifacts/`, checks `artifact.json.updatedAt` against the retention window, revalidates candidates immediately before deletion, and atomically renames expired artifact directories to managed cleanup staging (`~/.ai-artifacts/managed/cleanup/<artifactId>-<uuid>/`). Recursive deletion runs only on staged paths. Per-artifact atomic rename resolves multi-window races without a global lock. `EPERM`/`EBUSY`/`EACCES` errors skip the candidate without aborting the run. Legacy, malformed, mismatched-ID, linked, or escaped entries are skipped. Leftover staging entries from crashes are drained at the next activation. The cleanup process also prunes expired entries in `~/.ai-artifacts/conversation-registry/` and removes empty legacy v1 conversation folders while preserving empty v2 Work Sessions.
- Missing-handle contract: when an exact artifact handle no longer exists (retention cleanup, manual deletion, or filesystem loss), load/inspect/wait/advance/reconnect return `ARTIFACT_NOT_FOUND` with `retryable: false` and `useSameArtifactHandle: false`. Active waiters detect a missing directory and terminate instead of waiting indefinitely. While the directory exists and `.artifact-update.lock` is present, they skip submission reads and keep waiting; a temporarily absent manifest during commit/rollback is not deletion. Missing lifecycle files outside a transaction still fail validation. No tombstone, search-for-replacement, or recreation is attempted.
- Installer cleanup recognizes only extension-managed MCP blocks, hook entries, scripts, runtime files under `~/.ai-artifacts/managed/`, legacy `~/.vscode/ai-artifacts/` assets, registry snapshots, and managed skill directories. Unrelated user configuration is preserved, and user review data in `~/.ai-artifacts/artifacts/` is retained on uninstall. Uninstall does not run retention cleanup; cleanup staging in `~/.ai-artifacts/managed/cleanup/` may be removed by uninstall since it is managed state, and any artifact there has already passed the deletion commit point.

## Extension watcher and editor opening

Markdown links in Artifact Review use separate typed messages: `openLocalFile` accepts absolute local paths and local `file://` URLs, while `openExternal` retains its HTTP/HTTPS/mailto allowlist. The extension host decodes the file link, verifies that its target is an existing regular file, and opens it with `vscode.window.showTextDocument`. Directories and missing files use the existing webview error channel. Relative paths are not resolved. Opening a link does not mutate artifact lifecycle state, and the shared renderer's What's New content mode retains its external-only link policy.

The extension validates and creates the global collection root before registering a `RelativePattern` watcher for direct-child `artifact-connection.json` creation and change. Every extension window receives the filesystem event, performs bounded retry for transient create/replace races, and revalidates the root, artifact directory, connection file, manifest binding, and linked-path safety on every read attempt. A window ignores the request unless `connection.windowInstanceId` matches its own stable instance ID. The matching window may call `vscode.openWith` even when unfocused, provided `agentPlus.autoOpenArtifactReview` is enabled. Disabling auto-open does not prevent MCP from committing routing state.

Each window deduplicates successfully handled `openRequestId` values and coalesces concurrent work by canonical artifact path. Failed opens are not permanently deduplicated, so a later event can retry. Different artifacts remain independent, and VS Code's single-editor-per-document contract performs the final reuse/reveal behavior. Non-target validation failures remain silent in that window; the target window reports actionable failures without opening an unsafe artifact.

The manual **AI Artifacts: Open Artifact Review** command accepts an `artifact.md` URI from Explorer, the Markdown editor context menu, or its editor-tab context menu. Without an explicit URI, it uses the active `artifact.md` or Artifact Review URI when available, then falls back to a file picker rooted at the global collection. Every entry point shares the same `ArtifactReviewOpenCoordinator` and fail-closed validation boundary as the watcher: the artifact must be a direct child of the global collection with a valid schema-v6 manifest, matching identity, and safe non-linked paths before `vscode.openWith` runs. This provides a user-controlled return path when a chat `artifactLink` opens a normal Markdown editor rather than the review editor. The **AI Artifacts: Search Artifact** command (`agentPlus.searchArtifact`) provides an extension-local search UI via VS Code Quick Pick. It enumerates valid schema-v6 direct children in `~/.ai-artifacts/artifacts/` with bounded concurrency, filters in-memory on normalized title (accent-insensitive, case-insensitive, deterministic order, capped at 1,000 items), and revalidates and opens the selected artifact through the shared `ArtifactReviewOpenCoordinator`. Search is strictly local to the current window and does not call MCP, invoke window routing, or mutate connection state. Users can copy the exact artifact handle into AI chat using the **Inspect artifact** button in the review header. A chat `artifactLink` is only a regular file link and may open a normal Markdown editor depending on the client.

## Work Sessions and Activity Bar sidebar navigation

The legacy conversation drawer has been replaced by a first-class Work Session architecture and dedicated Activity Bar view:

1. **AI Artifacts Activity Bar View**: Provides two views (`agentPlus.recentArtifacts` and `agentPlus.sessions`), defaulted to visible on first load:
   - **Recent Artifacts**: Displays the 20 most recently updated artifacts (sorted by `updatedAt` desc) with quick access to full title search via **View all...** (`agentPlus.searchArtifact`).
   - **Sessions**: Displays v2 Work Sessions with their session type labels (`Conversation`, `Project`, `Feature`, `Fix`, or custom types), artifact counts, and dynamic `updatedAt` recency.
   - **Filter & Search Sessions**: Header actions on the Sessions view provide window-local filtering by session type (`agentPlus.filterSessions`, showing the active filter in `TreeView.description` and resetting to `All Types` if the selected type is deleted) and accent/case-insensitive title search across all v2 Work Sessions (`agentPlus.searchSessions`, independent of the active sidebar filter).
   - **Session Types Management**: A gear action (`agentPlus.manageSessionTypes`) on the Sessions view header opens a native VS Code QuickPick to create, rename, or delete global session types.
   - **Migration Detection**: Displays the count of legacy v1 conversations with an action to launch bulk migration.
2. **Work Session Manager (`agentPlus.workSession`)**: Opening a session renders `SessionApp` in a two-column layout:
   - **Main Column**: Displays the `Working` artifact zone, expanding to full width when the side panel is collapsed.
   - **Collapsible Side Panel**: Ordered as `Session Type` (with quick pick to assign or create a type) → `Instructions` (fixed-height Markdown textarea with explicit **Save**) → `References` zone → `Archived` zone. Per-session panel expanded/collapsed state is persisted in extension `globalState` (`workSessions.panelExpanded.<sessionId>`, default `true`).
   - **Artifact Organization**: Each artifact card provides a menu to move across `Working` / `References` / `Archived`, reorder (`Move Up` / `Move Down`), or remove the artifact from the session without deleting the underlying artifact files. Clicking an available artifact card opens it in the review editor via the shared `ArtifactReviewOpenCoordinator`.
   - **Scoped Refresh & Draft Preservation**: `ConversationArtifactService` classifies registry, manifest, and session-types watcher events into scoped `WorkSessionDataChange` batches (`metadata`, `membership`, `layout`, `artifact`, `types`, `support`). Unrelated background refreshes (artifact manifest edits, membership/layout updates, title/type changes) update only their target UI sections and never reset unsaved `Instructions` text or focus. If the persisted `instructions.md` file on disk actually changes, `WorkSessionProvider` emits `workSessionInstructionsPatch` to update the textarea.
3. **Review App Sessions Navigation, Start Work Session & Direct Inspect**:
   - The Review App header provides a **Sessions** button (when the artifact belongs to one or more sessions) to reveal or select the session in the sidebar.
   - If the artifact has no session memberships, the header displays **Start a work session**, allowing the user to create a session, register the artifact into Working, and copy the session connect prompt.
   - Clicking **Inspect artifact** copies a direct 2-line inspect prompt to clipboard without dialog popups.
4. **Single & Bulk Migration**: The coordinator (`src/extension/session-migration-command.ts`) provides single migration (migrates v1 to v2 with a backup `conversation.v1.backup.json` and opens the session) and bulk migration with native confirmation dialogs and VS Code progress notification reporting. All Session Quick Input flows and notifications use unified English wording while preserving user-authored session titles, instructions, and type labels.

## Agent Session context and freshness

`create-review-artifact` requires its five artifact tools; `work-session` requires `join_session` for Session entry and refresh. The server keeps no per-chat active Session. No active Session means standalone by default; active S supplies `artifactConversationId: S` to create/inspect unless standalone was explicitly requested. `conversationName` without an ID explicitly creates New; a successful Join/New replaces chat context, while standalone `session: null` and failed calls preserve it. Session errors stop automated recovery rather than clearing IDs or creating replacements.

Join-only returns `{ session }` with metadata, effective Instructions, `instructionsPath`, and ordered Working/References/Archived catalogs. Available items carry exact `artifactDirectory` and `artifactPath`; unavailable items carry only their ID and availability marker. Join with an artifact returns `{ session, inspection }` from the shared inspect core. Only that branch performs artifact inspection and its requested membership/routing/takeover behavior.

For user-requested organization, agents may directly edit `layout.json` in the directory of the returned `instructionsPath`; no additional Session-directory or layout-path field is returned. The Session skill reads current membership and layout, moves or reorders existing IDs across the three arrays while preserving unrelated placement, then refreshes through Join-only. Membership files remain authoritative; removing an ID from layout alone does not remove membership, and the Session's Archived zone does not change global artifact Archive state. Layout writes do not affect Session recency and use last-write-wins without user/agent conflict handling. Agents may edit Instructions Markdown when requested but must not directly edit Session metadata, membership files, or managed artifact lifecycle files outside the explicit AI-feedback exception above.

Before related work, the Session skill reads current Instructions from `instructionsPath` or reuses fresh Instructions returned for that request. Requests for latest artifacts, recent changes, current Session contents, or a current overview refresh the catalog before selecting an artifact, even if an older exact path is known. Otherwise known exact artifacts are read directly from their current Markdown paths. Unknown targets require a fresh catalog; ambiguous targets require clarification. Fresh context already returned for the same request is reused. Successful non-null Session results replace rather than merge the active catalog; exact artifact review handles remain separate. This is on-demand freshness, with no background push and no takeover merely to read references.

## Deployment and filesystem support

The supported v1.1.x topology requires a local desktop VS Code-compatible extension host and MCP process running as the same OS user, resolving the same home, and seeing the same `~/.ai-artifacts/` filesystem. Windows, macOS, and Linux are the declared local targets. Remote SSH, WSL, dev containers, Codespaces, browser/virtual workspaces, and split-host topologies are unsupported in v1.1.x because their producer/consumer filesystem boundary has not passed the release matrix.

## Grouped manual integration commands

`AI Artifacts: Installer` (`agentPlus.installer`) and `AI Artifacts: Uninstall` (`agentPlus.uninstall`) use native multi-select QuickPick controllers in `src/extension/integration-install-command.ts` and `src/extension/integration-uninstall-command.ts`. Installer calls `listInstallableClients(context)` to list all seven supported clients cleanly with `Detected` / `Saved` badges and configuration paths (without running slow per-client `check()` calls or showing live status/error rows); Uninstall calls `listInstallerClients(context)` to show current integration status, detection/saved badges, configuration paths, and diagnostic details (isolating driver check exceptions as `configuration-conflict` rows without aborting the other clients). Installer preselects detected or saved clients and accepts OK, the title-bar Run button, or Enter; Uninstall starts with no selection and accepts OK or Enter. Dismissal or confirming an empty selection makes no changes.

All manual install entry points (`AI Artifacts: Installer`, `AI Artifacts: Install All Detected Integrations`, and all seven single-client install commands) submit to the Integration Manager and route outcomes through one shared notification helper (`src/extension/install-notification.ts`), with UI/support refresh (`onDidInstall`) isolated from installation error handling so post-install refresh failures are logged diagnostically without turning a completed install into an error notification:

- `installSelectedIntegrations()` calls shared base setup once, then invokes each selected driver's private `install()` sequentially without a post-install `check()` pass. Only successful clients are merged into `installed-clients.json`. Per-client exceptions are collected without stopping the remaining selected drivers; a shared setup failure stops before the client loop. On success or partial failure (at least one installed client), the shared notifier offers `Reload Window` alongside outside-window client restart/new-chat guidance; when all selected clients fail or a shared error throws, it shows one error without `Reload Window`.
- `uninstallSelectedIntegrations()` removes only each selected driver's private configuration/skills and, on successful removal or an already-unconfigured result, its saved client ID. The command requests `cleanupBase: true`. Before removal, the coordinator assesses usage across all supported clients; after each successful selected removal, it reassesses that client. Shared cleanup runs once after the loop only when no client still uses or may use the shared assets, saved-state inspection is determinate, and no selected removal failed. Unselected consumers, failed removals, or indeterminate state retain the base. User artifacts, Work Sessions, and unrelated configuration remain preserved.

Drivers do not run shared setup or shared cleanup. Manual batch operations and automatic upgrade reuse the same driver factory, shared asset synchronization, receipts, and skill replacement helpers, while retaining their separate target selection, mutation, and notification policies. Automatic upgrade does not open either picker or change saved client selections.

The earlier all-detected and per-client commands remain publicly contributed (`Reinstall` aliases still call `installAllIntegrations` once cleanly via shared `install-notification.ts`). Activation onboarding and automatic-upgrade error notifications direct users to **`AI Artifacts: Installer`**. `AI Artifacts: Verify All Integrations` remains an explicit manual command owning `Ready` / `outdated` / `missing` / `configuration-conflict` reporting. The grouped commands are the recommended manual entry points; the legacy entry points have not been removed or redirected to the pickers.

## Integration asset versioning and skill customization

The extension tracks integration assets independently from the extension package version. `src/shared/contracts.ts` defines numeric, monotonically increasing `MCP_VERSION`, `CREATE_REVIEW_ARTIFACT_SKILL_VERSION`, and `WORK_SESSION_SKILL_VERSION` values; they are not SemVer. `SKILL_VERSION` aliases only the artifact skill version. A schema-v1 receipt at `~/.ai-artifacts/managed/integration-version.json` tracks the installed MCP runtime plus skill versions (`skills` for `create-review-artifact` and `sessionSkills` for `work-session`) for `.agents`, `.claude`, and Antigravity (`.gemini/config`) independently as steps complete (without implying read-back content verification). Separately, manual install and uninstall commands record successful client selections in `~/.ai-artifacts/managed/installed-clients.json` (never including `"agents"` and never rewritten by automatic upgrade).

The Integration Manager commits receipts only for completed steps. Base setup writes the MCP runtime plus both `.agents` skill versions after all three packaged assets succeed (and automatic upgrade commits each completed shared asset incrementally); Claude writes both of its own skill receipts after its independent install succeeds, and Antigravity writes both of its own skill receipts after its independent install succeeds. The receipt may therefore represent a valid partial install; an invalid, absent, or mismatched asset entry is stale and is never replaced by an assumed baseline.

During extension activation, the activation controller (`src/extension/integration-activation.ts`) asynchronously reads `~/.ai-artifacts/managed/integration-version.json` once before any client detection or upgrade:

- **Read I/O failure:** reports a diagnostic and shows one error notification citing **`AI Artifacts: Installer`** without running detection or upgrade.
- **`missing` receipt:** skips client detection and automatic upgrade completely. If `globalState` flag `installer.onboardingAccepted` is `false` (default), it shows one Info notification inviting the user with **`Run Installer`** (dismissing keeps the flag `false`; clicking persists `true` before opening `AI Artifacts: Installer`, even if the user cancels the picker). If the flag is already `true` while the receipt remains missing, activation stays silent and never converts the flag into an upgrade trigger.
- **`valid` or `invalid` receipt:** hands the exact `ExistingInstalledIntegrationVersionReadResult` snapshot directly to `runAutomaticIntegrationUpgrade` -> `upgradeDetectedIntegrations(context, installedVersion)` without emitting a setup prompt.

Within `upgradeDetectedIntegrations(context, installedVersion)` and `runAutomaticIntegrationUpgrade()` (`src/extension/upgrade-notification.ts`):

- Target resolution merges `saved ∪ detected` clients from `installed-clients.json` and client `isDetected()` across all seven drivers (`copilot`, `cursor`, `codex`, `claude`, `windsurf`, `cline`, `antigravity`). If no clients are selected, the coordinator returns an empty report immediately without reading receipts or mutating disk, and the upgrade controller stays silent (no empty-report freshness warning).
- When targets are selected, the coordinator computes staleness from the caller-provided receipt snapshot (without re-reading `integration-version.json` to reclassify missing vs existing), deploys stale shared assets (`mcp`, `.agents` skills) once, and commits receipts per completed shared asset without cleaning up legacy hooks/files or writing client selections. Each selected driver runs `upgrade(context)` without calling `check()` post-upgrade, keeping definition reconciliations (such as selectively patching `[mcp_servers.ai_artifacts.tools.join_session]` in Codex when targeting MCP 12+) idempotent while leaving current assets and configs untouched. Missing/conflicting setups are left unmutated without emitting `setup-required` warnings; driver exceptions become `failed` without blocking remaining drivers or committing incomplete client receipts.
- After settlement, support/sidebar views refresh once in `finally` (with refresh failures isolated diagnostically). Empty, unchanged, and healthy `updated` reports stay silent; one error notification (`View Installation Guide`, naming **`AI Artifacts: Installer`**) is shown only when at least one client reports `failed` or the coordinator rejects. Updating files on disk does not restart running AI clients or live chats; users still restart external clients and start a new chat to load updated runtime/skills. An extension-only update with current receipts performs no asset rewrites and shows no popup.

Skill reinstall and auto-upgrade snapshot the target before mutation, merge a valid non-official YAML `description:` and the exact contents of the `USER CUSTOM RULES` block into the packaged `SKILL.md`, stage the complete directory, and then swap it atomically. `.agents`, `.claude`, and Antigravity (`.gemini/config`) are merged from their own targets and never inherit each other's customizations. Skill customization applies only to `create-review-artifact`; `work-session` is deployed as official assets without customization. Unsupported or malformed frontmatter/markers fail closed before the first target rename and identify the target that the user must repair. `Ready` (reported by manual **`AI Artifacts: Verify All Integrations`**) means the official assets are current after this merge; it does not validate the behavioral compatibility of custom rules.

## Compatibility

The current implementation uses numeric MCP version 12, review skill version 4 (`SKILL_VERSION = 4`), work session skill version 1, artifact schema v6, Work Session schema v2 (with explicit user-triggered single or bulk legacy v1 migration; MCP access to v1 returns `CONVERSATION_MIGRATION_REQUIRED`), and optional connection schema v1. The schema-v6 transition remains a hard protocol cutoff: the MCP tool catalog contains exactly six tools (including `join_session`) with `resolve_artifact_window` replacing `resolve_artifact_workspace`, while schema-v3/v4/v5 and workspace-local lifecycles remain untouched on disk but are not parsed, opened, advanced, or migrated. Extension activation gates first-time users on receipt presence for `Run Installer` onboarding and automatically upgrades stale installed integrations for existing users across saved and detected clients without prompting for a manual click; manual commands (`AI Artifacts: Installer`, `AI Artifacts: Verify All Integrations`) remain the explicit paths for setup, repair, and readiness inspection. Extension-only updates with current receipts leave installed assets untouched. After an upgrade or manual install updates runtime assets or tool definitions, users reload the editor window or restart external AI clients and start a fresh chat. Rolling back across incompatible asset versions requires reinstalling the matching runtime/skill. Optional connection files remain preserved user artifact data and may be ignored by older code; they are never deleted during rollback or uninstall.
